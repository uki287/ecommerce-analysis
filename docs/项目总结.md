# Olist 电商分析项目 · 全流程总结

> 一句话：把 Olist 巴西电商的 9 张原始 CSV，做成一套「可复现的指标底表 + 10 类图表 + 9 页 Power BI 看板 + 操作手册」的完整分析链路。
> 代码入口：`src/run_analysis.py` ｜ 图表入口：`notebooks/02_olist_10_charts.py` ｜ 看板：`F:\power bi\data-test-v2.pbix`

## 一、项目定位

| 项 | 内容 |
|---|---|
| 数据类型 | 公开数据集（Olist Brazilian E-Commerce），9 张关系型 CSV |
| 分析窗口 | 2017-01-01 ～ 2018-08-31，20 个自然月 |
| 数据规模 | 99,441 个订单、约 112k 商品行、约 100 万地理行 |
| 有效订单 | 97,905（剔除 canceled / unavailable / 无商品明细） |
| 技术栈 | Python（pandas/numpy/matplotlib）、Jupyter、Power BI（DAX）、PBIP 工程化 |
| 交付物 | 7 张明细表、28 张图表底表、1 个 Excel 工作簿、10 张图、9 页看板、25 页手册 |

**它不是"画十张图"的练习**，而是一条完整链路：原始表 → 清洗 → 数据模型 → 指标口径 → 图表底表 → 可视化 → BI 看板 → 文档。

## 三、八个步骤，每步在做什么

### 步骤 1 · 数据接入与结构校验（`src/data_loader.py`）

**做什么**：读 9 张表，强制类型、校验字段、记录时间范围。

- ID 类字段（订单号、客户号、商品号、卖家号、邮编前缀）**全部强制为字符串**，避免 pandas 把 `00000` 读成数字丢掉前导零；
- 日期字段统一解析为 datetime，解析失败的记 `NaT` 而不是报错中断；
- 用 `EXPECTED_COLUMNS` 做字段级校验，缺列直接抛错（防止上游换表结构）；
- 文本字段去空格、统一小写（州缩写、状态、支付方式），中文/葡萄牙语原文保留；
- 打印每张表的行数与日期区间，作为运行日志的一部分。

**为什么重要**：后面所有关联都靠订单号/客户号，一旦 ID 被转成数字，`customer_id` 关联会静默丢失。

### 步骤 2 · 维表清洗与标准化（`src/prepare.py` 前段）

**做什么**：把 4 张维表洗干净。

- **地理表**（约 100 万行）：按 `zip_code_prefix` 取经纬度**中位数**（同一邮编有多个点），再用巴西经纬度范围 `lat[-35,6] / lng[-75,-33]` 剔除 40 个境外异常点，得到 19,010 个坐标点；
- **商品表**：合并英文品类翻译表，缺失品类统一归为 `Unknown`，保留 `category_pt` 和 `category_en` 两列；
- **卖家表**：补上 ZIP 对应的经纬度，供地图使用；
- **评论表**：一个订单可能有多条评论，取最新一条作为订单级评分，同时保留 `review_score_mean`、`review_count`，避免丢信息。

### 步骤 3 · 事实表构建与三种粒度（`src/prepare.py` 后段）

**做什么**：把散落的明细聚成可分析的订单级模型。

- `orders_master`（一行一单）：商品件数、商品金额、运费、商品+运费总额、支付金额、分期数、最新评分、下单/审批/承运/送达时间、**送达天数**、**是否迟到**、是否在窗口内、是否有效订单；
- `items_enriched`（一行一订单商品）：订单信息 + 商品 + 品类 + 卖家 + 地理，用于下钻；
- `order_category` / `order_seller`（一行一订单-品类 / 订单-卖家）：解决"一单多品类、多卖家"导致的重复计数问题；
- `customer_rfm`（一行一客户）：用 `customer_unique_id` 聚合 R、F、M 三个维度，按**五分位**打分，再映射成 8 类客群（重要价值、沉睡、流失预警等）；
- `cohort_retention`：以客户**首购月份**为队列，计算之后每个自然月的留存。

**关键设计**：客户主键必须用 `customer_unique_id`——`customer_id` 是订单级的，同一个人下两单会有两个 `customer_id`，用它算复购率会直接算成 0。

### 步骤 4 · 指标体系（`src/metrics.py`）

**做什么**：只做聚合，不画图，输出 28 张"图表底表"。

- 总览：`overview_kpis`（KPI 卡片用的 10 个数字）；
- 时间：`monthly_kpis`、`monthly_growth`；
- 品类：`category_kpis`、`category_monthly`、`product_kpis`、`top_products`；
- 地域：`state_kpis`、`state_monthly`；
- 卖家：`seller_kpis`、`seller_pareto`（累计 GMV 占比，直接支撑帕累托图）；
- 支付：`payment_type_kpis`、`installment_distribution`；
- 评价：`review_distribution`、`review_by_delivery`；
- 履约：`delivery_distribution`、`delivery_delay_distribution`；
- 客户：`rfm_segment_summary`、`rfm_score_matrix`、`cohort_retention` / `_wide`。

**口径纪律**：
- 比例一律输出 0–1 小数，格式交给 Excel/BI；
- 金额单位统一 BRL；
- 迟到 = 实际送达日期 > 预计送达日期；
- 订单级指标在品类/卖家粒度下钻时会**重复计数**，文档里明确写了"收入可加、订单数不可加"。

### 步骤 5 · 数据质量报告（`src/quality.py`）

**做什么**：把"数据有多脏"变成一张可查的表，而不是悄悄删掉。

本次运行暴露的问题（都保留在 `data_quality_report.csv`）：

- 99,441 个订单里 775 个没有商品明细（多为 unavailable/canceled）；
- 551 个订单有多条评论，814 个重复 `review_id`；
- 8 个 delivered 订单缺实际送达日期；
- 9 条 0 元支付（voucher / not_defined）；
- 417 个订单的支付总额与"商品+运费"差异 > 0.01；
- 610 个商品无品类，2 个品类无英文翻译。

**原则**：主键/外键/日期/金额/覆盖率逐项检查，标 `WARN` 或 `INFO`，**不静默覆盖原始值**。

### 步骤 6 · 中文显示层（`src/localize_zh.py`）

**做什么**：生成一份"给人看"的中文副本，但不动英文标准表。

- 表头、订单状态、支付方式、州、品类、RFM 客群、金额/时长区间全部中文化；
- ID、日期、文件名保留原值（保证还能关联）；
- 巴西城市名保留葡萄牙语原文，避免错误翻译地名；
- 产物：`tables_zh/`（28 个 CSV）、`processed_zh/`（7 个明细表）、`Olist_analysis_tables_zh.xlsx`（28 个工作表）。

### 步骤 7 · 可视化（`notebooks/02_olist_10_charts.py`）

**做什么**：10 张图覆盖 5 个分析视角。

| 视角 | 图 | 类型 |
|---|---|---|
| 趋势 | 月度 GMV 与订单数 | 双轴组合图 |
| 结构 | 品类 GMV Top10、支付构成 | 横向条形图、环形图 |
| 分布 | 送达天数分布、品类订单金额分布 | 直方图、箱线图 |
| 关联 | 品类规模/评分/迟到率 | 气泡散点图 |
| 集中度 | 卖家帕累托、州级多指标 | 帕累托、雷达图 |
| 地域 | 州级 GMV 与迟到率 | 地理气泡图 |
| 留存 | Cohort 留存 | 热力矩阵 |

输出：`report/figures/*.png` + `report/Olist_10_charts.html`（不用 Jupyter 也能看）。

### 步骤 8 · BI 看板与文档（Power BI + `scripts/create_powerbi_manual.py`）

**做什么**：把分析结论搬进可交互的看板。

- 9 页：01 月度趋势、02 品类结构、03 支付构成、04 品类规模与体验、05 州级地图、06 配送时效、07 箱线图与雷达、08 Cohort 留存、09 卖家集中度；
- DAX 度量值：有效订单数、商品 GMV、含运费 GMV、客单价、复购客户率、迟到率、累计 GMV 占比；
- 交互：TopN 视觉筛选（品类 Top10、卖家 Top100）、条件格式、帕累托累计线；
- 工程化：用 PBIP（文本工程）管理报告定义，改完由 Desktop 另存回 PBIX——因为 PBIX 报告层有完整性校验，外部直接改会损坏；
- 文档：25 页 Word 操作手册（导入、建模、10 张图逐图步骤、DAX、发布刷新、排错）+ 指标口径表。

## 四、关键设计决策（面试最容易被问）

| 决策 | 原因 |
|---|---|
| 客户分析用 `customer_unique_id` | `customer_id` 是订单级的，用它算复购会算成 0 |
| `gmv` 与 `gross_order_value` 分开 | 前者看商品销售规模，后者看用户实付；混用会让品类排名和 AOV 同时失真 |
| `payment_value` 只用于对账 | 优惠券、分摊、舍入导致它与"商品+运费"有差额，强行对齐等于篡改收入 |
| 品类/卖家单独建 order-category / order-seller 表 | 一单多品类，直接 join 会重复计数 |
| 迟到用"实际 > 预计" | 这是平台承诺口径，比"平均天数"更能反映体验 |
| 长尾排名加样本量过滤 | 评论数和迟到率在样本 <30 时波动极大，排名会失真 |
| 质量检查只标记不删除 | 删掉异常会让总数对不上，也无法向业务解释口径 |

## 五、局限（写进简历/答辩时主动说）

1. **没有成本和流量数据**，算不出利润、ROI、CAC；
2. **公开数据、单一平台**，结论不能直接外推到其他市场；
3. 箱线图和雷达图在 BI 里是**静态 PNG**，不随筛选联动；
4. 看板**没有切片器**，时间/品类/州还不能统一切换；
5. 相关不等于因果：迟到与差评强相关，但没做因果推断。

## 六、可复用的东西

- `src/metrics.py` 的 `build_*` 函数可以按主题增删，新指标注册进 `build_all_metrics()` 就自动进 CSV/Excel；
- 中文映射表（州、品类、支付、RFM）可以直接搬到别的巴西电商数据集；
- 质量报告 + manifest（`report/run_manifest.json` 记录每次运行的输入输出与行数）是可复现性的关键；
- PBIP + 脚本化改报告定义的流程，可以复用到任何 Power BI 交付项目。
